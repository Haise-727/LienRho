# Architecture — what runs, and where

## The allocation loop, as PS-5 specifies it

```
   ┌──────────── LEARN ◄─── SETTLE ◄─── FINANCE ◄─── MATCH
   │             (gap)                                  ▲
   ▼                                                    │
INVOICE ──► VERIFY ──► ASSESS RISK ──► DISCOVER ──► GENERATE ──► COMPARE
                                       CAPITAL       OFFERS
```

Every stage exists except the feedback edge. `LEARN` is marked as a gap rather
than drawn as if built.

## The matching engine — `frontend/src/lib/market/`

The part that must not drift. Every file is pure and DB-free except `server.ts`.

| File | Responsibility |
|---|---|
| `types.ts` | Cross-track contract. **Zero imports by design.** |
| `money.ts` | Integer paise, basis points, business-day dates |
| `offer-math.ts` | The four formulas, one implementation |
| `utility.ts` | Derives the gates from the cash position |
| `score.ts` | Lexicographic gates, then cost ranking |
| `pareto.ts` | Non-dominated frontier + degeneracy guard |
| `allocate.ts` | Capacity, minimum tickets, concentration, syndication |
| `commit.ts` | Atomic allocation — conditional update under transaction |
| `clear.ts` | `clearOpportunity()` — the whole pipeline |
| `server.ts` | The only query that feeds clearing |

### Three decisions that carry the design

**Money is integer paise. Rates are integer basis points.**
The worked example turns on a **3 basis point** gap. IEEE-754 drift across
advance → discount → net → effective-cost is the same order of magnitude, so a
float would let rounding noise pick the winner.

**The gates are derived at read time, not stored.**
`sufficiencyFloor` and `timingDeadline` are **null in the database on purpose**.
They come from the cash position when clearing runs — which is what makes
"we infer need from the supplier's real position" true rather than a value
somebody wrote into a column.

**Bids are never generated by the logic that scores them.**
Provider pricing reads only that provider's mandate. If the scorer could see
`costOfFunds`, the market would be one function agreeing with itself and every
figure would be circular.

## The degeneracy guard — the check that found our own bug

If one offer beats every other on **cash, cost and speed simultaneously**, the
bid set is broken rather than the market competitive. No arithmetic test catches
this, because each individual calculation is correct.

It fired immediately, against our own generator. The first provider panel gave
the fintech the highest advance, no fee, instant settlement *and* a spread below
the bank's — **210 of 279 opportunities flagged**. That is not a market, it is a
price list with one entry.

Two fixes, both how the real thing works:

- **The fintech now carries a convenience premium.** You pay for speed, so it wins on cash and settlement and loses on cost.
- **Providers have minimum tickets.** A ₹2,500 flat fee on a ₹50,000 invoice is 5% of face — a bank bidding there is not competing, it is losing. Real desks decline below their minimum.

Four-offer sets went from **71/274 degenerate to 0/257** at 5000 invoices.

## Data pipeline

```
generate_tally.py  →  Tally XML  →  TallyConnector (real parser)  →  canonical JSON
                                                                          │
                              ┌───────────────────────────────────────────┤
                              ▼                                           ▼
                    analyse.ts (5000, in memory)              seed-corpus.ts (48, Postgres)
                    statistical claims                        the browsable board
```

Two paths on purpose, and they must not be confused:

- **`analyse.ts`** samples pressure uniformly and is tuned toward no outcome. The statistics come from here.
- **`seed-corpus.ts`** is curated to demonstrate. 280 rows is right for a claim and wrong for a screen.

The distinction is written at both ends of the code.

## The tool boundary — the project's first rule

**No language model computes a financial figure. Anywhere.**

Verified by reading all three agents:

- `lender_bidding_agent` — every financial field copied from the provider profile; LLM output reaches only `notes`
- `supplier_agent` — pure function over cash-need ratio and time-to-due; LLM output reaches only `rationale`
- `market_clearing_agent` — LLM output reaches only `clearing_summary`
- `llm.complete()` returns `None` on any failure, and **every** caller has a deterministic fallback

Degrade, never halt — through one seam that tests can monkeypatch.

This mattered in a previous build because it protected a legal filing. Here it
protects priced capital and a settlement obligation, so the bar is higher.

## Known limitations

1. **Allocation concurrency is guarded, not proven.** `commit.ts` uses a
   conditional update so the check and decrement are one atomic statement. The
   tests argue the shape against a fake row; none runs concurrent transactions
   against real Postgres.

2. **Buyer concentration is the cap, not the remainder.** Exposure already taken
   against a buyer is not tracked, so it binds correctly for a first deal and is
   optimistic afterwards.

3. **Two economics implementations exist.** `lib/money.ts` (Decimal, for the
   ledger) and `lib/market/offer-math.ts` (integer paise, for scoring). They
   agree today; a cross-check test is open as issue #11.

4. **Risk is seeded.** `probabilityOfDefault` is a column, not a model output.
